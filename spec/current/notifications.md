# サーバー通知

オーナー限定のアカウント設定から「サーバーエラーの通知設定」を開き、`/settings/notifications` で通知の有効化、配信先、Webhook URL、通知レベルの下限、対象サービスを変更する。初期状態は無効、Discord / ERROR以上 / Web API・ActivityPub・Node.jsプロセスを選択する。通知先アダプターはDiscord・Slack・汎用JSON Webhook。対象サービスと送信先は独立して追加できる。

Webhook URLはパスキー認証済みオーナーだけが登録・更新・削除でき、既存のホスト暗号化鍵を用いたAES-256-GCM暗号文として永続SQLiteに保存する。画面/API/HTMLにはURL、暗号文、認証情報を返さず、設定済みフラグのみ返す。URLを空欄にして保存すると既存URLを維持する。配信先を変更する際には対応する新URLが必要。削除時には通知を無効化する。鍵が未設定ならURLは登録できず、既存の暗号文は読み出せない。テスト送信はオーナーが明示操作した場合だけ実行する。

通知イベントは `service`、`level`、`code` の型付き情報を持つ。通常は選択サービスかつ下限以上のレベルのみ配送する。通知先へ転送するのは固定文言とイベントコード・時刻だけで、リクエストURL・body・Cookie・例外メッセージ・stack・APIキーを含めない。API/ActivityPubのサーバーエラーとプロセスのエラーを観測する。誤送信を避けるため、同一コード/サービスの通知は1分間に1件に集約し、同時送信数を制限する。通知の失敗はサイトや投稿操作を失敗させない。

送信時にはHTTPSのみを許し、Discord/Slackは正規ホストとURL形式を検証する。汎用Webhookもホストのローカル・予約済みIP、内部ドメイン、IPリテラル、認証情報付きURLを拒否する。DNS解決結果は接続時にチェックし、リダイレクトせず、タイムアウトを設定する。配信先の応答本文を記録しない。

対象はアプリプロセス内のイベントであり、ホストのsystemd、Docker daemon、停止したプロセスやマシンの障害を検知する外形監視ではない。致命的なプロセス終了時のネットワーク送信はbest effortであり到達保証しない。これらは独立したホスト監視が必要。

API: owner-only `GET/PUT/DELETE /api/notifications` はそれぞれ安全な設定状態取得・更新・Webhook削除。owner-only `POST /api/notifications` は明示的なテスト通知。更新/削除/テストはOrigin一致とレート制限を必須とし、全応答に `Cache-Control: no-store`。バックアップと復元には永続SQLiteの設定・暗号文と、別途同一のホスト暗号化鍵の保全が必要。
