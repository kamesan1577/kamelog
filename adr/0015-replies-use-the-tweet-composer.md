# ADR 0015: 返信を通常つぶやき投稿フローへ統合する

## 状況

詳細画面の返信フォームだけが画像添付、X Web Intent、Fediverse選択、下書き保護を持たず、通常のつぶやきと操作感が異なっていた。また、返信のActivityPub Noteに親参照がなく、公開タイムラインでは親子が別投稿に見えていた。

## 決定

- 返信は既存の `parentId` を使い、tweetの本文・画像・共有・配信選択と同じ入力契約で保存する。専用の返信テーブルやActorは追加しない。
- 返信下書きにも `parentId` を保存する。親の存在・tweet種別は保存時と公開時に検証し、削除済み親を通常投稿へ暗黙変換しない。
- 配信対象の返信Noteには親のlocal object URLを `inReplyTo` として設定する。親が現在Fediverse非公開なら、新規配信だけを拒否し、ローカル保存と既存子の編集は妨げない。
- 公開タイムラインは公開tweet全件を親参照から純粋関数でグループ化し、検索やタグが子に一致した場合も親文脈を残して親→子孫順に表示する。循環・欠落親は独立起点として扱う。
- 詳細画面の投稿配列、選択、遷移、返信追加はNotebookが所有し、返信詳細はDOM探索・portalに依存せず同じReactツリーで描画する。

## 理由

既存APIと投稿JSONにある親参照を再利用すれば、通常投稿・返信・ActivityPubの正本を分岐させずに一致させられる。表示だけを独立コンポーネントに閉じず、フィルタ後のグループ化を共有することで、返信が検索結果から消える不整合を避けられる。

## 影響

既存の配信済み投稿を遡って再配送しない。配送失敗はローカル投稿成功を取り消さず、既存のdurable queueとworkerで扱う。返信UIの位置と既存カードの外観は維持し、追加状態は既存デザイントークン境界内に置く。
