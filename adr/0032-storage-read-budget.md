# ADR 0032: 常駐監視と公開閲覧のDB読み取りを減らす

状態: 採用

Issue #308でWorkers FreeのDurable Objects読み取り枠超過が報告された。
画像の公開認可で全投稿を取得し、投稿数に応じたタグ・推論リンクの追加SQLを発行していた。
配送workerのhealthcheckも30秒ごとに配送履歴全体を集計していた。
これらはコードで確認できる負荷増幅要因であり、当日の500万行の内訳は本番メトリクスで別途確定する。

投稿一覧は投稿・タグ・推論リンクを3 SQLで取得し、Mapで結合する。
個別投稿は主キーで取得する。
媒体認可にはスキーマ13の`post_media_refs`と媒体IDの索引を使う。
スキーマ12からの初回更新で既存投稿を走査し、投稿の保存と同じトランザクションで参照を更新する。
投稿削除では外部キーのCASCADEで参照を失効させ、下書きは参照表へ含めない。
公開認可と媒体レスポンスはキャッシュせず、編集・削除による失効を即時反映する。
旧スキーマ12の入力・出力と、新スキーマの検証付きバックアップ・復元を維持する。

`/api/health`はDBを読まないlivenessとする。
`/api/ready`で保存先とスキーマを確認し、更新時の確認にはこちらを使う。
配送workerのlivenessはコンテナ内の時刻・PIDを持つheartbeatファイルで確認する。
配送のheartbeatとclaimは1つのドメインRPCへまとめ、クラウドの待機間隔15秒を維持する。
保存先のエラーでは同一プロセス内で指数待機し、コンテナ再起動による再試行の増幅を防ぐ。
保存先の正常性はlivenessだけで判定せず、readinessと配送診断を使う。

sitemapはブログのID・日時だけを取得する。
オーナーのFederation timelineはカーソルと件数をSQLへ渡し、各ソースから1ページ分と次ページ確認用1件を取得する。
公開ホーム・Timelineと投稿一覧APIは既存のクライアント検索・タグ・スレッド契約を維持するため、引き続き一覧全体を取得する。
この一覧の読み取り行数は投稿・タグ数に比例するため、無料枠内で無制限の閲覧を保証しない。

Durable SQL cursorを最後まで消費してから`rowsRead`・`rowsWritten`を計測する。
`STORAGE_DIAGNOSTICS=true`の場合だけ、許可済み操作名と数値をログと認証済みRPCレスポンスヘッダーへ出力する。
SQL、バインド値、本文、トークン、世代IDは記録しない。
既定では診断ログを出さない。
架空データ0/10/100/1000件をローカルworkerdで実行し、SQL数と実際の読み取り行数の予算を検証する。
Workersリクエスト数、SQL数、読み取り行数を区別する。
